This page is an **internal verification harness** for the Panel Hardening epic (issues #145–#154). It documents the hostile-host test scenario and serves as the URL target for a /verify-ui screenshot dispatch by the manager.

## Level-5 automated gate (F33 + F24)

The panel's hostile-host CSS isolation is now backed by an automated **browser-mode** test that runs in CI on every PR via Playwright Chromium:

```
packages/zdtp/src/__tests__/hostile-host-isolation.browser.test.tsx
```

This converts the manual DevTools harness below into a deterministic regression gate. The test injects the hostile CSS **before** the panel CSS (real deployment order) and asserts key computed styles survive.

### Automated hostile CSS fixture

The hostile fixture used in the gate covers the acceptance-criteria scenarios:

```css
h1, h2, h3, h4, h5, h6 {
  font-size: 4rem !important;
  margin: 2rem 0 !important;
  color: red !important;
}
p, ul, li, table {
  margin: 3rem !important;
  padding: 2rem !important;
  color: red !important;
}
* { box-sizing: content-box; }
svg { fill: red !important; }
html { font-size: 20px; }
:focus { outline: none; }
```

### What the gate asserts

| Assertion | Hostile rule countered |
|---|---|
| `box-sizing: border-box` on shell descendants | `* { box-sizing: content-box }` |
| Tab-section heading `font-size: 13px` | `h1-h6 { font-size: 4rem !important }` + root 20px |
| Tab-section heading `margin: 0px` | `h1-h6 { margin: 2rem 0 !important }` |
| SVG `fill` inside shell is not red | `svg { fill: red !important }` |
| `role=button` div background: transparent | `button { … }` (doesn't apply to divs) |
| Panel shell `position:fixed` at expected viewport coords | transform-ancestor on the page (F24) |

### SVG fill defensive reset — why `!important` is required

The scoped SVG reset in `panel.css` uses `fill: currentColor !important`:

```css
:where(.tokenpanel-shell) svg {
  fill: currentColor !important;
}
```

A hostile `svg { fill: red !important }` is a same-origin `!important` declaration at specificity `0-0-1`. The panel's rule (also `!important`, also `0-0-1`) wins because **the panel CSS is injected at runtime AFTER host CSS** — at equal specificity and both `!important`, the later cascade position wins. Removing the `!important` from the panel rule would allow the hostile rule to win regardless of cascade order.

### Transform-ancestor note (F24)

A common position:fixed trap: CSS `transform`, `filter`, `perspective`, `backdrop-filter`, `will-change: transform/filter`, `contain: paint/layout/strict`, or `content-visibility: auto/hidden` on any ancestor of a `position:fixed` element causes the element to resolve against that ancestor instead of the viewport.

The panel appends its root div directly to `document.body` in `ensureMounted()` (index.tsx). This means the panel root is a **sibling** of host page content elements that carry transforms, not a descendant. A sibling's transform does not create a containing block for its sibling's `position:fixed` descendants. The automated gate verifies this with two complementary cases: sibling (protected) and inner-descendant (trapped — confirms the trap is real).

**Known limitation:** if `body` or `html` itself carries a transform (e.g. `html { filter: invert(1) }` dark-mode hacks, `body { transform: translateZ(0) }` from page-transition libraries), ALL `position:fixed` elements inside body are trapped — including the panel. This cannot be fixed without changing the panel's containing-block strategy. To reproduce, paste in DevTools:

```js
document.body.style.transform = 'translateZ(0)';
// Then open the panel — it positions relative to body, not the viewport.
```

## What is a hostile host?

A hostile host is an application whose global CSS aggressively resets or overrides semantic HTML element styles. Examples include Tailwind CSS preflight, CSS resets (normalize.css, ress, etc.), and hand-rolled resets that use `all: revert` or tag-level selectors.

The panel must render correctly inside any host environment — its markup may not rely on browser default styles that the host has stripped away.

## Hostile CSS injected on this page

The following stylesheet simulates the most aggressive host overrides we expect to encounter. It is injected via a `<style>` element **before** the panel mounts so every panel element renders under these constraints.

```css
h1, h2, h3, h4, h5, h6 { font-size: 4rem !important; margin: 2rem 0 !important; color: red !important; }
button { all: revert !important; background: hotpink !important; padding: 2rem !important; font-size: 2rem !important; }
p, ul, li, section, header, article, aside, nav { margin: 3rem !important; padding: 2rem !important; }
code, pre { font-family: "Comic Sans MS" !important; background: yellow !important; }
details, summary { font-size: 3rem !important; list-style: square !important; }
svg, path { fill: hotpink !important; stroke: lime !important; transform: scale(2) !important; }
* { box-shadow: inset 0 0 0 2px lime !important; }
```

### Step 2 — Inject the hostile stylesheet

Open DevTools console in the running example app and paste:

```js
const s = document.createElement('style');
s.textContent = `
  h1, h2, h3, h4, h5, h6 { font-size: 4rem !important; margin: 2rem 0 !important; color: red !important; }
  button { all: revert !important; background: hotpink !important; padding: 2rem !important; font-size: 2rem !important; }
  p, ul, li, section, header, article, aside, nav { margin: 3rem !important; padding: 2rem !important; }
  code, pre { font-family: "Comic Sans MS" !important; background: yellow !important; }
  details, summary { font-size: 3rem !important; list-style: square !important; }
  svg, path { fill: hotpink !important; stroke: lime !important; transform: scale(2) !important; }
  * { box-shadow: inset 0 0 0 2px lime !important; }
`;
document.head.prepend(s);
```

### Step 3 — Open the panel and exercise every tab

```js
// Astro example:
window.astro.toggleDesignPanel();

// zfb examples:
window.zfb.toggleDesignPanel();
```

Exercise every tab (Spacing, Typography, Size, Colour, etc.) and open every modal (Export, Import JSON, Apply). Confirm:

- No element inside `.tokenpanel-shell` or modal overlays appears broken, stretched, or uses the hostile colours.
- Buttons and interactive controls render at normal size (they are `div[role=button]`, not native `button`).
- Headings inside the panel (tier section labels) render at normal size (they are `div[role=heading]`, not `h3`/`h4`).
- The JSON preview areas (export modal, apply modal) may show `pre` bleed — see Static-grep findings below.
- SVG icons do not paint hotpink/lime (they are scoped by the `:where(.tokenpanel-shell) svg` reset).

### Summary

Wave 2 is **mostly complete**: headings, lists, buttons, sectioning elements, and disclosure elements are all replaced in production markup. **Two regressions remain**: `<pre>` in the export modal (line 202) and `<pre>` in the apply modal success view (line 766). Both are code/preformatted display elements that will inherit hostile `pre` overrides (font-family, background). These should be tracked as a follow-up fix sub-issue.

### Recommended follow-up

Open a new sub-issue against epic #145:

- File: src/export-modal.tsx:202 — replace `<pre>` with a styled `<div>` carrying `white-space: pre` + `font-family: monospace` in CSS.
- File: src/apply-modal.tsx:766 — same replacement.
- Neither fix should change visual output when no hostile CSS is present.

## A11y note

Keyboard accessibility under the hostile host **cannot be verified by static analysis**. The hostile CSS (`button { all: revert !important }`) would only affect native `<button>` elements — and static grep confirms none remain in production markup. However focus-ring and keyboard-nav behaviour must be validated in a real browser with hostile CSS active. Flag as a follow-up for the manager's `/verify-ui` dispatch.
