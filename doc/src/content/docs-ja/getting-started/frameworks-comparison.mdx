パネルの公開インターフェースは、1 回の `configurePanel({...})` 呼び出しと、自分でレンダリングするシェルです。そのため、どのホストでも組み込みの形は同じです。0.9.0 以降、シェルは Preact ではなく、パネルに同梱された zudo-react ランタイムでレンダリングされます。ホスト側の React、Preact、zudo-react のツリーとランタイムを共有しないため、パネルのために Preact をインストールしたり compat エイリアスを設定したりする必要はありません。ホストごとに異なるのは、誰が `configurePanel` を呼ぶか、ホストがどうナビゲーションするか、開発時の Apply プロキシをどう登録するかです。スタイルの import は差異になりません。パネルは初回マウント時にスタイルシートを自己注入するため、どのフレームワークでも利用側の CSS import は不要です。

このページでは横並びで概要を比較します。完全なコードは[サンプル](./examples.mdx)ページを参照してください。各フレームワークのライブデモとソースリポジトリへのリンクがあります。5 つのサンプルはすべて、公開済みの `@takazudo/zdtp` 0.9.1 を厳密に固定しています。

## 比較

| 手順 | Astro | Vite + React | Next.js (App Router) | ZFB | ZFB + Wind |
| --- | --- | --- | --- | --- | --- |
| パッケージのインストール | `pnpm add @takazudo/zdtp`（ホスト独自のアイランド用に `@astrojs/preact` も追加） | 同じ。Preact は不要 | 同じ。Preact は不要 | 同じ。Preact は不要 | 同じ。Preact も `tailwindcss` も不要 |
| `PanelConfig` の定義 | ホスト側の TS ファイル 1 つ | 同じ | 同じ | 同じ | 同じ |
| ホストのマウント | レイアウト内の `<DesignTokenPanelHost>` | `useEffect` から `mountPanel()` を呼ぶ。ローカルのアダプターがパネルを遅延 import して `configurePanel(...)` を呼ぶ | ルートレイアウトに置いた `'use client'` コンポーネントの `useEffect` から `mountPanel()` を呼ぶ | クライアント専用の `<Island>` で、`getScope().onActivate()` がアダプターをマウント | ZFB と同じ |
| 副作用 script | レイアウトの script で `import('@takazudo/zdtp/astro/host-adapter')` | 不要 | 不要 | 不要（ネイティブな有効化処理） | ZFB と同じ |
| スタイル import | 不要（自己注入） | 不要（自己注入） | 不要（自己注入） | 不要（自己注入） | 不要（自己注入） |
| ナビゲーション | `<ClientRouter />` の view transition。ホストアダプターがスワップのたびにパネルを再マウント | 1 つのドキュメント内で `HashRouter`。`prose.html` は別のフルページエントリー | App Router のクライアントナビゲーション | ネイティブなマルチページ読み込み（`<ClientRouter />` なし） | ZFB ネイティブの `<ClientRouter />` |
| ユーティリティ CSS | 該当なし | 該当なし | 該当なし | 該当なし（`wind: false`） | 組み込みの Wind。`wind.tokens` がユーティリティを記述済みの `--zfbtw-*` 値へ対応付ける |
| Apply プロキシ（開発時） | `astro.config.ts` 内の Vite `server.proxy` | Vite `server.proxy` | 開発専用ルート `app/api/dev/apply/route.dev.ts` | `devMiddleware` と `previewMiddleware` を登録するプラグイン | ZFB と同じ |
| Apply エンドポイント URL | `/api/dev/apply` | `/api/dev/apply` | `/api/dev/apply/`（末尾スラッシュ付き） | `/api/dev/apply` | `/api/dev/apply` |
| Apply パイプライン bin | dev script から `concurrently` で `zdtp-server` を起動 | 同じ | 同じ | 同じ。`scripts/launch.mjs` から起動 | ZFB と同じ |

共通する点:

- `PanelConfig` の形式とすべてのフィールド。
- console API。`window.<consoleNamespace>.{show,hide,toggle}DesignPanel()` はすべてのホストで追加され、各サンプルのトップバーのボタンはこれを呼びます。
- 固定名の `window.zdtp.{show,hide,toggle}()` グローバル。`consoleNamespace` に依存しない別名として、namespaced console API の上に追加されます。
- `storagePrefix` に基づくストレージキーの導出方法。
- Apply パイプラインの動作。`applyEndpoint` への POST はどのホストでも同じです。
- [`data-zdtp-version`](../reference/configure-panel.mdx#ライフサイクルヘルパー-ビルドバージョンマーカー-data-zdtp-version) マーカー。パネルを開いている間、どのデモでも `document.querySelector('.tokenpanel-shell')?.dataset.zdtpVersion` は `"0.9.1"` を返します。

異なる点:

- `configurePanel(...)` を**自分で**呼ぶか（Vite + React、Next.js、ZFB、ZFB + Wind）、Astro の**ホストアダプター**が代わりに呼ぶか。
- ナビゲーション方式。Astro の `<ClientRouter />`（スワップのライフサイクルはホストアダプターが処理）、Vite + React の `HashRouter`、Next の App Router、ZFB のネイティブなマルチページ読み込み、Wind の ZFB ネイティブ `<ClientRouter />` のいずれか。
- Apply プロキシの登録方法。Vite の `server.proxy`（Astro と Vite + React）、開発専用の Next ルート、ZFB プラグインの `devMiddleware` / `previewMiddleware` フックのいずれか。
- ZFB 組み込みの Wind の `wind.tokens` マッピングを通じて、ユーティリティクラスがパネルのトークンへ解決されるかどうか（ZFB + Wind のみ）。

## Astro

Astro ではマウント処理をエントリーが担当します。共有レイアウトに `<DesignTokenPanelHost>` を置き、レイアウトの script からホストアダプターを読み込みます。スタイルはパネルが自己注入します。このサンプルは独自のインタラクティブなアイランドのために `@astrojs/preact` も使いますが、これはホスト側のコードです。パネルはホストの Preact を使いません。

```astro
---
// src/layouts/Layout.astro
import { ClientRouter } from 'astro:transitions';
import DesignTokenPanelHost from '@takazudo/zdtp/astro/DesignTokenPanelHost.astro';
import { panelConfig } from '../config/panel-config';
---

<!doctype html>
<html lang="en">
  <head>
    <ClientRouter />
  </head>
  <body>
    <slot />
    <DesignTokenPanelHost config={panelConfig} />
  </body>
</html>

<script>
  // A dynamic import, so the bundler keeps this side-effect load.
  const adapterReady = import('@takazudo/zdtp/astro/host-adapter');

  // The topbar button waits for the adapter before toggling.
  document.addEventListener('click', (event) => {
    if (!(event.target instanceof Element) || !event.target.closest('[data-design-panel-toggle]')) return;
    void adapterReady.then(() => window.astro?.toggleDesignPanel?.());
  });
</script>
```

`astro dev` の実行中は、`astro.config.ts` の Vite サーバーが `/api/dev/apply` を bin へプロキシします。実装例: [GitHub ソース](https://github.com/Takazudo/zudo-design-token-panel-example-astro)。

## Vite + React

Vite + React サンプルは、`react` → `preact/compat` のエイリアスも compat shim も使わない、本物の React 18 アプリです。アプリシェルが `useEffect` から小さなローカルアダプターを呼びます。アダプターは `window.vr.*` を追加し、パネルを遅延 import するため、パネルは初期チャンクに含まれません。そのうえで、読み込んだモジュールの `configurePanel(...)` を呼びます。

```tsx
// src/components/AppShell.tsx (excerpt)
import { useEffect } from 'react';
import { mountPanel } from '../lib/mount-panel';

export function AppShell({ children }: { children: React.ReactNode }) {
  useEffect(() => {
    mountPanel(); // idempotent; StrictMode-safe
  }, []);
  return (
    <>
      <button type="button" onClick={() => window.vr?.toggleDesignPanel?.()}>
        Open Design Token Panel
      </button>
      {children}
    </>
  );
}
```

```ts
// src/lib/mount-panel.ts (shape)
import { panelConfig } from '../config/panel-config';

let modulePromise: Promise<typeof import('@takazudo/zdtp')> | null = null;

function loadPanel() {
  modulePromise ??= import('@takazudo/zdtp').then((mod) => {
    mod.configurePanel(panelConfig);
    return mod;
  });
  return modulePromise;
}

export function mountPanel(): void {
  window.vr = {
    toggleDesignPanel: async () => (await loadPanel()).toggleDesignPanel(),
    // showDesignPanel / hideDesignPanel follow the same pattern
  };
}
```

アプリ内のルートは `HashRouter` を使います。ハッシュの変更ではドキュメントが置き換わらないため、ライフサイクルアダプターは不要です。prose ページは別の Vite エントリー `prose.html` で、アプリとの行き来はフルページ読み込みになります。`vite` の開発時は、`server.proxy` が `/api/dev/apply` を bin へ転送します。

実装例: [GitHub ソース](https://github.com/Takazudo/zudo-design-token-panel-example-vite-react)。

## Next.js (App Router)

Next.js では、パネルをブラウザーでだけ読み込むために `'use client'` 境界が必要です。このサンプルは、小さなクライアントコンポーネントをルートレイアウトで 1 回だけレンダリングします。このコンポーネントが `useEffect` から同じ種類の遅延アダプターを呼び、トップバーのボタンが `window.nx.toggleDesignPanel()` を呼びます。

```tsx
// app/_components/PanelBootstrap.tsx
'use client';

import { useEffect } from 'react';
import { mountPanel } from '../../src/lib/mount-panel';

export default function PanelBootstrap() {
  useEffect(() => {
    mountPanel();
  }, []);
  return null;
}
```

```tsx
// app/layout.tsx
import PanelBootstrap from './_components/PanelBootstrap';

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>
        {children}
        <PanelBootstrap />
      </body>
    </html>
  );
}
```

<Note title="useEffect を使う理由">
  `configurePanel(...)` は同期的で、同じ値に対しては冪等です。アダプターを `useEffect` から呼ぶと、サーバーレンダリング中に実行されず、インストール用モジュールをそれ以外では何もしない状態に保てます。代わりにモジュール初期化時に呼ぶ場合は、そのファイルがクライアントバンドルからだけ読み込まれるようにしてください。
</Note>

**Apply ルート。** App Router には、Vite の `server.proxy` のような開発サーバーのプロキシ設定がありません。代わりに、このサンプルは開発専用の API ルート `app/api/dev/apply/route.dev.ts` を用意し、POST を bin へ転送します。パネルは `/api/dev/apply/` へ POST します。`trailingSlash: true` を設定しているため、末尾スラッシュ付きが正規の URL です。`pnpm build` は `NEXT_BUILD_TARGET=export` を設定して、`out/` に静的エクスポートを出力します。このモードでは `pageExtensions` が既定値のままなので、エクスポーターは `.dev.ts` ファイルを認識しません。

```ts
// next.config.ts (excerpt)
const isExportBuild = process.env.NEXT_BUILD_TARGET === 'export';

const nextConfig = {
  trailingSlash: true,
  pageExtensions: isExportBuild
    ? ['ts', 'tsx', 'mdx']
    : ['ts', 'tsx', 'dev.ts', 'dev.tsx', 'mdx'],
  ...(isExportBuild ? { output: 'export' as const } : {}),
};
```

多層防御として、このルートは `NODE_ENV === 'production'` のときに 404 を返します。

実装例: [GitHub ソース](https://github.com/Takazudo/zudo-design-token-panel-example-nextjs)。

## ZFB

[ZFB](https://github.com/Takazudo/zudo-front-builder)（zudo-front-builder）は、作者が別リポジトリで開発しているビルドオーケストレーターです。ZFB サンプルでは、ZFB プロジェクトへパネルを組み込む方法を示します。

ZFB 3〜5 は zudo-react アイランドを使います。パネルは中身に関与しない、自分でレンダリングするウィジェットとして扱います。`getScope().onActivate()` 内で `@takazudo/zdtp` を遅延 import して、そこで設定します。破棄後に完了した import はキャンセルし、クリーンアップ時にハンドルを破棄します。パネルは独自のランタイムを持つため、ホストには Preact も Preact 用の JSX 設定も不要です。このサンプルは ZFB と zfb-runtime 4.3.0 を固定し、クライアント専用のアイランドでアダプターをマウントします。

```tsx
// components/app-shell.tsx (excerpt)
<Island when="load" ssrFallback={null}>
  <PanelMount />
</Island>
```

通常の ZFB サンプルは `<ClientRouter />` を使わないため、戻る・進むを含むすべてのナビゲーションがネイティブなフルドキュメント読み込みになります。`zfb.config.ts` では `wind: false` も設定しています。

このドキュメントサイトは、ZFB 5.1.5 上の zudo-doc 9.1.0 を使い、ネイティブ zudo-react レンダリングと Wind CSS を採用しています。サイトに埋め込まれたパネルは固定した npm リリースで、プレイグラウンドと最小構成デモはワークスペースのパネルビルドを使います。以前の ZFB 2 連携は Preact アイランドと Astro ホストアダプターを使っていました。その再マウント回帰テストは独立した ZFB 2.20.3 / zudo-doc 5.27.0 のフィクスチャーに残してあるため、現在のドキュメントを固定し直す必要はありませんでした。

開発時の Apply プロキシの接続方法もここでは異なります。Vite には `server.proxy`、Next には開発専用ルートがあります。ZFB は代わりにプラグインフックを提供しており、このサンプルは 1 つのハンドラーを `zfb dev` と `zfb preview` の両方に登録します。

```ts
// zfb.config.ts
import { defineConfig } from '@takazudo/zfb/config';

export default defineConfig({
  base: '/',
  wind: false,
  plugins: [{ name: './plugins/dev-apply-proxy.mjs' }],
});
```

```js
// plugins/dev-apply-proxy.mjs
function registerApplyProxy(ctx) {
  // The handler returns { status, headers, body }; register a full request path.
  ctx.register('/api/dev/apply', proxyHandler);
}

export default {
  name: 'dev-apply-proxy',
  devMiddleware: registerApplyProxy, // zfb dev
  previewMiddleware: registerApplyProxy, // zfb preview
};
```

どちらのフックも `zfb build` では実行されないため、デプロイされる静的出力にプロキシは含まれません。

**Apply エンドポイント URL。** ZFB [#229](https://github.com/Takazudo/zudo-front-builder/issues/229) により、登録したミドルウェアのパスは `base` の下にスコープされます。このサンプルは `base: '/'` なので、プレフィックスなしの `/api/dev/apply` がそのまま base プレフィックス付きのパスになります。同じ構成をルート以外の `base` にデプロイする場合は、Apply のパスにも同じ `base` を付けてください。リポジトリの [`PROBE-REPORT.md`](https://github.com/Takazudo/zudo-design-token-panel-example-zfb/blob/main/PROBE-REPORT.md) は、サンプルがルート以外の `base` で配信されていた 2026 年 5 月 9 日の調査を記録した過去のレポートです。背景情報としてだけ参照してください。

実装例: [GitHub ソース](https://github.com/Takazudo/zudo-design-token-panel-example-zfb)。

## ZFB + Wind

ZFB + Wind サンプルは、通常の ZFB サンプルのアイランド構成と、`devMiddleware` / `previewMiddleware` による Apply プロキシを共有します。異なる点は 3 つです。

- **ナビゲーション。** `@takazudo/zfb-runtime` の ZFB ネイティブ `<ClientRouter fallback="animate" />` を使います。トップバーとサイドナビは `data-zfb-transition-persist` によってスワップ後も保持されます。
- **ユーティリティ CSS。** ZFB 組み込みの Wind を使います。`tailwindcss` 依存も `@theme` ブロックもありません。
- **トークンの対応付け。** `styles/global.css` の `:root` に記述した `--zfbtw-*` カスタムプロパティが、パネルでの編集と Apply の基準のままです。`zfb.config.ts` の `wind.tokens` が、ユーティリティ名をそれらのプロパティへ対応付けます。

```css
/* styles/global.css (excerpt): the values the panel edits and Apply rewrites */
:root {
  --zfbtw-palette-1: #2d6cdf;
  --zfbtw-color-primary: var(--zfbtw-palette-1);
  --zfbtw-hsp-md: 1rem;
  --zfbtw-scale-base: 1rem;
  --zfbtw-text-body: var(--zfbtw-scale-base);
}
```

```ts
// zfb.config.ts (excerpt)
export default defineConfig({
  base: '/',
  plugins: [{ name: './plugins/dev-apply-proxy.mjs' }],
  wind: {
    spec: 1,
    reset: 'owned-v1',
    tokens: {
      colors: { primary: 'var(--zfbtw-color-primary)' },
      spacing: { 'hsp-md': 'var(--zfbtw-hsp-md)' },
      fontSizes: { body: { size: 'var(--zfbtw-text-body)' } },
    },
  },
});
```

Wind の各トークンは `var(--zfbtw-*)` 参照へ解決されるため、`bg-primary`、`px-hsp-md`、`text-body` などのユーティリティはパネルでの編集にそのまま追従します。たとえばパネルで `--zfbtw-text-body` を変更すると、`text-body` を使うすべての要素が更新されます。prose ページは、同じ `--zfbtw-*` トークンを使って `@layer components` で要素をスタイリングしています。

Apply エンドポイント URL は通常の ZFB サンプルと同じで、`base: '/'` に対してプレフィックスなしの `/api/dev/apply` を使います。

実装例: [GitHub ソース](https://github.com/Takazudo/zudo-design-token-panel-example-zfb-tailwind)。
